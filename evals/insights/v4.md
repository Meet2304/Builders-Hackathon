# Insights: v4 moves 1–2 (`method/v4` @ `c9e1a0c`)

Written before Eval's v4 report. Sources:
- Method's quick numbers: 1,772–1,795 instructions per line at 20M, against 2,610 for v3.
- Eval's v3 per-phase counters (`evals/results/v3.md`, "Per-phase instructions and cycles").
- **My own instruction counts**, all on this Mac (`/usr/bin/time -l`, instructions retired):
  - dev at NCPU=1 for v3 `29b64bf`, v4 move 1 `e62060c` and v4 move 2 `c9e1a0c`, each built from its commit;
  - a single-threaded stage microbenchmark on 2.6M real seed-42 event lines (`v4_stagebench/`, verbatim copies of
    the engine's functions).
- I ran these while Eval held the lock, at the lowest priority (`nice 19`), for about 10 s of one core in total.
  Instruction counts don't depend on load, so they're exact; I took no timings.

## 1. The G1 "miss" is a misattribution: G1 delivered and G2 didn't

**Each commit's instructions on dev (NCPU=1, 1,072,115 event lines):**

| Build | Instructions | Per event line | Δ |
| --- | ---: | ---: | ---: |
| v3 `29b64bf` | 2.832 G | 2,641 | |
| v4 move 1 `e62060c` (G1 quote-aware fast path) | 2.104 G | 1,962 | **−679** |
| v4 move 2 `c9e1a0c` (G2 16 B rows + counting sort) | 2.004 G | 1,869 | **−93** |

The endpoints agree with Method's (v3 2,631 and move 2 1,855 per line). **Method's middle number, 2,628 for move 1,
can't be right.** It was most likely measured on a stale or v3 binary. Method should re-measure `e62060c` and correct
the log, because "split_fields on quoted lines was never the cost on M5" is false and would steer future scan work
wrongly.

**The scan path alone confirms it** (stage microbenchmark, 2.6M seed-42 lines, NEON, instructions per line after
subtracting the file load):

| Scan path | Instr/line |
| --- | ---: |
| memchr line iteration only | 70 |
| memchr + `split_fields` on every line (v1) | 887 |
| v3 `for_each_record` (79% of lines fall back to `split_fields`) | **875** |
| **v4 `for_each_record` (quote-aware, 100% fast)** | **291** |
| v3 / v4 with SWAR | 1,049 / 464 |

**My model, checked against these numbers:**
- **G1 was modelled about right.** I predicted ≈ −470; the measurement is −584 on event lines, and −679 per line
  including clicks and links.
- **G2 was over-modelled.** I predicted ≈ −470 and got −93.
  - Replacing pdqsort with a counting sort removed comparison work, but the sessions phase's instructions are
    elsewhere: the per-row person interning, the session loop, attribution and `flush_user`.
  - G2 should still pay off in cycles and at 60M (16 B rows, less traffic, no `PEv` copy). Eval's v4 report will
    show it.
  - The **sessions kernel (Explorer 3) is now the main lever there**, not the sort.

**Could the scorer differ? Only upward.**
- `split_fields` is scalar byte-loop code with no ISA-specific part, so the instructions saved carry over to x86
  unchanged.
- Cascade Lake runs branchy byte loops at a much lower IPC than the M5 (Eval: events parse IPC 3.45 here). So in
  **board seconds** G1 is worth at least its instruction share: ≈ 0.4 s at 20M by the 28.8 G/s rule.
- The SSE2 classifier (4 × 16 B per mask) costs about the same per 64 B as NEON's, so the fast path costs the same.

## 3. Re-ranked by board seconds, and what's still unowned

The rule: 100 instructions per line ≈ 0.075 board seconds at 20M (28.8 G instr/s), and ≈ 0.22 s on the 60M final.

| Rank | Item | Owner | Instr/line saved | Board s saved 20M / 60M |
| --- | --- | --- | ---: | ---: |
| 1 | Sessions + attribution kernel, 430 → 60 | Explorer 3 (assigned) | ≈ 370 | **0.28 / 0.8** |
| 2 | **Scan loop, 302 → 70:** line-at-a-time extraction from the comma mask, no per-bit type test, and AVX2 or AVX-512BW behind the startup self-test | **UNOWNED** | ≈ 230 (+ ≈ 25 in clicks) | **0.19 / 0.55** |
| 3 | **Probe + emit path, ≈ 235 → 50:** a ring of (slot, row index) instead of 56 B `PendEv`; arena writes without capacity checks; hash once, then reuse it for both bucket indices | **UNOWNED** | ≈ 185 | **0.14 / 0.4** |
| 4 | ID packer, 196 → 35 for events, plus 2 IDs per click | Explorer 2 kernel → Method (assigned) | ≈ 160 + 40 | 0.15 / 0.45 |
| 5 | Output, 130 → 10 | Explorer 3 (assigned) | ≈ 120 | 0.09 / 0.2 |
| 6 | **Timestamps, 152 → 50:** ingest is always F1, so give it a dedicated straight-line F1 path. Return a sentinel instead of `Option`; a branch-light F3-13 path; clicks share it | **UNOWNED** | ≈ 100 (+ ≈ 15 in clicks) | **0.09 / 0.25** |
| 7 | Category lookup only for purchases | Method (assigned) | ≈ 100 (my measurement; Method's estimate was 57–67) | 0.075 / 0.22 |
| 8 | Links: 69 → 33, and parallelism 2.9 → 7 | Method (assigned) | 36, plus the serial tail | 0.03 + ≈ 0.08 tail / 0.3 |
| 9 | **Clicks residual, 146 → 30:** Ck at 24 B, a click-specific straight-line validate, and items 2, 4 and 6 applied | **UNOWNED**; it follows from 2, 4 and 6 | ≈ 50 beyond those | 0.04 / 0.1 |
| 10 | L2-sized partitions + skew scheduling | Sol (assigned) | cycles, not instructions | ≈ 0.02 / 0.3 (it removes the dedup ×4.2 and sessions ×3.6 superlinearity) |

**The assigned items** (1, 4, 5, 7, 8) take ≈ 1,830 to ≈ 1,000 per line, which predicts ≈ 0.75 s on the board.
**The unowned items** (2, 3, 6, 9) take it on to ≈ 400, which predicts ≈ 0.30 s. Reaching 375 needs every item
at its target and the 95 of slack mostly unused.

**Proposed owners for the unowned items:**
- **Scan loop (2): Explorer 2,** after the packer. It owns the parse path and SIMD, and the scan loop is the same
  kind of kernel as the packer. Acceptance: `v4_stagebench` mode 4 ≤ 80 instr/line, plus Method's G1 unit test
  (1.2M random lines vs `split_fields`) on both classifiers.
- **Probe + emit (3): Method.** It owns the row layout it just changed, and the change touches `EvOut` and
  `flush`. Acceptance: dev instructions per line −150 or more, and every gate.
- **Timestamps (6): Explorer (Sol).** Sol wrote the window decoder (`d1da46e`) and has its differential harness.
  Acceptance: `v4_stagebench` mode 8 − mode 7 ≤ 60, and the v3-review `cases_ts.py` plus the decoder unit test.
- **Clicks residual (9): Method,** once 2, 4 and 6 land.

## 4. Requests for Eval

- **Per-commit instruction checks:** record instructions per line for every commit Method reports, built from that
  commit, the way §1 did. A move's gain is only "measured" when the binary is built from its own commit.
- **Run `evals/insights/v4_stagebench` in the quick profile** as a per-stage regression check for the event parse.
  It's single-threaded, about 1 s per mode, and counts instructions only.
- **The v4 full eval:** report cycles per row per phase next to instructions. G2's benefit should show up in
  cycles (sessions IPC on v3 was 3.04 at 20M) and in the 60M superlinear phases, not in instructions.

## 5. Confidence

- **High:** the per-commit counts (deterministic, and the endpoints match Method's), and the scan-path and
  stage-microbenchmark numbers (verbatim engine functions, on real lines).
- **Medium:** the split of v4's per-phase numbers (derived), and the ≈ 235 for probe and emit (a remainder).
- **Open:** how much G2 buys in cycles and at 60M. Eval's v4 report answers that.
